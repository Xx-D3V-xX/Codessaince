Overview & architecture

CreditGate converts applicant financial data into a transparent credit decision. The core design decisions (from CLAUDE.md):

  • Rules-first, ML-secondary — a configurable business rules engine (BRE) makes every final decision. An XGBoost model produces a risk signal the BRE can reference; it never decides on its own.
  • Two pipelines — INDIVIDUAL (salaried/self-employed) and MSME (business-owner), each with its own ruleset and model.
  • Everything versioned by insert, not update — rules, weighted-scoring config, recalibration offsets, and eligibility/pricing bands are never mutated in place. Editing inserts a new version row and closes out the old one, so a past decision's snapshot never changes underneath it.
  • One shared audit log — every state-changing action across the whole system writes through one entity-agnostic audit_log table.

Request flow: Frontend → FastAPI → Rules engine (Phase 4) → Exception routing (Phase 6) → Eligibility/pricing (Phase 7) → Postgres, with an XGBoost risk signal (Phase 5) feeding the pricing stage.

Running it locally

Every time you want to start it up

Backend and frontend are two fully independent processes — see the warning box below for why. Start the backend:

docker compose up -d
python -m alembic upgrade head
uvicorn src.api.main:app --reload

That's it for the backend — alembic upgrade head is a no-op if migrations are already applied, and the API loads the already-trained models from disk at startup, it never retrains them. Then, separately, start the frontend (see frontend/README.md):

python -m http.server 5500 --directory frontend

Open http://localhost:5500 for the test console, /api-reference for interactive Swagger docs, or stay here at /docs.

Why two processes, not one. This backend used to also serve the frontend directly (mounted under /app). uvicorn --reload watches the entire working directory by default, so any frontend-only edit — a .js/.html/.css change with nothing to do with the API — was restarting the whole backend process, which re-runs the ~1-minute, 8,000-applicant dataset build on every save. Splitting them into two processes (with CORS enabled on the backend) fixes that structurally: editing the frontend can never again restart the backend.

One-time setup (or whenever you deliberately want to reseed config / retrain)

Run this once after a fresh git clone, or any time you've wiped the data/ directory (it's gitignored — trained models and generated data don't travel with the repo) or want to intentionally regenerate the models:

# seed the default config — idempotent, safe to re-run any time, does NOT retrain anything
python -m src.rules.seed_rules
python -m src.scoring.seed_weighted_scoring
python -m src.scoring.recalibration
python -m src.pricing.seed_pricing

# train the two models — writes data/models/{individual,msme}/model.pkl
# only needed once; the API loads these files, it doesn't call this itself
python -m src.scoring.trainer
You do not need to retrain on every restart. Training writes .pkl files to data/models/; the API just reads them off disk each time it starts. Only re-run src.scoring.trainer if you've deleted that directory, regenerated the underlying applicant data, or actually want different model weights.

Authentication / authorization

Every endpoint below is open — no login, no API key, no session. The exception approve/reject endpoints have one piece of real, testable authorization logic (not authentication): they require an X-User-Role header matching the exception's level.

Header valueCan resolve
credit_ops_l1L1 exceptions
credit_ops_l2L2 exceptions
credit_headAny level (L1, L2, CREDIT_HEAD)

Anyone can set this header to anything — there is no verification that the caller actually holds that role. See src/api/deps.py for the same disclosure in code. A real deployment would sit this behind a proper identity provider.

Frontend

A basic internal test console at http://localhost:5500 (its own separate process — see frontend/README.md) — plain HTML/CSS/vanilla JS, no framework, no build step, talking to the API cross-origin via CORS. Explicitly scoped as basic/testing-only; a design pass is expected later. Five tabs: Submit, Decision, Rules Admin, Exception Queue, Audit — each a thin UI over the API above.

Testing — what was tested and how

Every test in this project runs against a real, live Postgres instance and real generated applicant data — never mocks, never fabricated dicts. Each script prints its own assertions and exits non-zero on failure.

test_api.pyEvery HTTP endpoint — submit/poll, PATCH, rerun, audit, role-gated approvalReal HTTP requests via FastAPI's TestClient (in-process ASGI) against the live API, DB, and models — not a mocked client.

The frontend itself (Phase 9) was verified by actually driving it in a real browser session — submit → decision → live rule edit → re-run → side-by-side comparison → exception queue → approve → audit — which is how two real bugs (an XSS gap and a header-merging bug that broke the exception-approval requests) were found and fixed; no automated script exercised the frontend's JS.

Build history, by phase

Full detail lives in PROGRESS.md and TODO.md in the repo. Summary:

  1. Phase 0 — synthetic applicant data generator (CopulaGAN), 8,000 applicants across master/bureau/bank/ITR/assets/alt-data/GST sources.
  2. Phase 1 — ingestion/adapter layer, Pydantic-validated per row.
  3. Phase 2 — cross-source derived features (obligation/income discrepancy, asset coverage).
  4. Phase 3 — Postgres schema (8 tables), Alembic migrations, versioned config pattern.
  5. Phase 4 — the rules engine: evaluation, AND-semantics, conflict resolution, rule CRUD.
  6. Phase 5 — weighted-scoring layer, two XGBoost models, disclosed proxy labels, SHAP, recalibration.
  7. Phase 6 — exception routing/resolution, honest (never-relabeled) audit trail.
  8. Phase 7 — eligibility & pricing, risk grade computed separately from the BRE outcome.
  9. Phase 8 — this API layer (async saga, live rule edits, rerun, audit, role-gated exceptions).
  10. Phase 9 — this basic frontend and this documentation page.

Known limitations (disclosed, not hidden)

  • No real authentication. See "Authentication / authorization" above.
  • In-memory dataset preload. The API loads all 8,000 applicants into memory once at startup (~1 minute) rather than serving per-request from a feature store — a deliberate MVP simplification, documented in src/api/dataset.py.
  • ML training labels are a disclosed synthetic proxy. No real repayment/default outcome exists in this dataset (inherent to any synthetic-policy demo). src/scoring/proxy_labels.py documents this explicitly — the BRE remains the sole real decision-maker regardless of model output.
  • Frontend is intentionally basic. Functional, not polished — a design pass is expected later per explicit project scope.
