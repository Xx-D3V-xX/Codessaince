- **Rules engine (Phase 4) — done and verified end-to-end against real applicant data and a live Postgres instance.** `src/rules/evaluator.py` evaluates every active rule for an applicant's pipeline against a flat field-value context, returning a three-valued `condition_met` (True/False/**None** for "couldn't evaluate, field missing" — deliberately never coerced to False, same null-vs-zero discipline as Phases 0-2) plus `evaluate_rule_groups()` implementing `rule_group` AND-semantics (a group fires only if every member is True; a known False short-circuits the group to False even alongside unknowns; any remaining unknown with no False makes the group's fired status None, never guessed). `src/rules/resolver.py::resolve_decision()` is the one function implementing all 5 steps of CLAUDE.md §3.4's precedence order (insufficient-data check, hard-reject-wins, exception routed to highest severity, count-based escalation, else STP) — a single clearly-named function per TODO.md's explicit instruction, not logic scattered across callers. `src/rules/context.py::pipeline_for()` branches SALARIED/SELF_EMPLOYED into the INDIVIDUAL ruleset and MSME/CORPORATE into the MSME ruleset (CLAUDE.md §3.1); `is_insufficient_data()` checks mandatory-source completeness before any rule runs. `src/rules/crud.py` implements create/edit/deactivate, with edit_rule() inserting a new version row and closing out the old one rather than mutating it — never touches a past row.

- **Weighted-scoring layer + ML integration (Phase 5) — done and verified against real Postgres, real applicant data, and real trained models.**
  - **Weighted-scoring layer** (`src/scoring/weighted_deviation.py`, CLAUDE.md §3.6): a new `weighted_scoring_config` DB table (Phase 3 predated this layer, so it wasn't in the original 7 tables — added now via Alembic migration `9b6a5cb597ee`, same insert-new-version pattern as `rules`). `normalized_deviation = clip((actual - base_limit) / reference_range, -1, 1)`, computed strictly before weighting; a `RiskDirection` enum (`HIGHER_IS_RISK`/`LOWER_IS_RISK`) sign-flips the deviation so it always reads as "toward risk" regardless of which side of `base_limit` is dangerous for that field — kept table-driven rather than hardcoding per-field polarity in Python. Every active field's `weighted_signal` for a pipeline sums into ONE new engineered feature (`admin_weighted_risk_signal`), matching CLAUDE.md §3.6's explicit "one XGBoost input feature, model schema never changes shape" design. Seeded with 12 default fields across both pipelines (`src/scoring/seed_weighted_scoring.py`).
  - **Two XGBoost models** (`src/scoring/trainer.py`, one per pipeline), each consuming the real `EngineeredApplicantFeatureVector` (78 features after encoding) + Phase 2's cross-source fields (already merged into the vector) + raw passthrough (`age`, `declared_income_monthly`, `requested_loan_amount`) + the admin-weighted composite signal — the exact training-feature architecture decision from earlier in this file. `src/scoring/feature_matrix.py` encodes band-categoricals ordinally by reusing `src/features/engine.py`'s own `*_BANDS` lists (one place band ordering is defined, never a second copy) and booleans as 0/1/NaN, leaving genuinely missing fields as NaN for XGBoost's native missing-value handling rather than a misleading 0-fill.
  - **`trainer.py` rebuilt from scratch, closing Known Issue #1.** The original hard-coded a proxy-label formula inline (`risk_score = np.where(bureau_score < 600, ...)`) using the exact step-threshold shape a real BRE rule would use, with its own fully disconnected hand-rolled feature engineering reading a parquet file (`applicant_profiles.parquet`) that no longer exists since the Phase 0 rebuild. The new trainer consumes the real adapter → engine → cross_source pipeline (no separate recomputation, and computed once and shared across both pipeline models rather than twice — caught and fixed during this rebuild). Deleted the now-fully-broken `train_model.py`, `test_model.py`, `test_inference.py` at repo root (all imported the old trainer's removed API and read the nonexistent parquet file — dead code, not working code, so deleted rather than patched).
  - **`src/scoring/proxy_labels.py` — the label-generation fix, disclosed explicitly rather than hidden.** No real repayment/default outcome exists in this dataset (inherent to any synthetic-policy demo, not fixable within this project's scope) — the fix isn't "use zero hardcoded thresholds," which is impossible without real outcome data, it's: (a) centralize and disclose the one heuristic in a single documented module rather than inline magic numbers duplicating BRE logic, and (b) make it a continuous, population-z-scored combination with a genuine Bernoulli stochastic draw (not a deterministic `> 0.5` cut) — two applicants with an identical profile can get different labels, real label noise the model can't fully recover, which is what makes an AUC of ~0.93 (not ~1.0) meaningful evidence the noise injection is actually doing something rather than the model just memorizing a deterministic formula.
  - **SHAP explainability** (`src/scoring/explain.py`) wired to both models, kept deliberately separate from the admin's explicit weighted-scoring signal — CLAUDE.md §3.6's own resolution to the acknowledged "double-weighting" limitation (the model's implicit SHAP-based importance and the admin's explicit weight compound rather than being cleanly separable from outside the model, so both are surfaced side by side rather than pretending they collapse into one honest number).
  - **Recalibration** (`src/scoring/recalibration.py`, lever 2 of CLAUDE.md §3.7's three levers — lever 3, full retraining, remains explicitly out of scope): `apply_recalibration()` adjusts the probability **after** the model produces it, at the probability-to-risk-grade mapping stage — not a multiplier on an input feature, which CLAUDE.md §3.7 already ruled out as unable to expand a shrunken value back toward its old relative standing. Offsets are read from the `recalibration_offsets` table (schema'd in Phase 3, unused until now) and go through the same shared `write_audit_log()` path as everything else — its "own audit trail" is its own `entity_type`, not a separate table. Seeded with neutral (0.0) offsets for every (pipeline, risk_grade) pair.
  - **Verified end-to-end with `test_scoring_pipeline.py`** against the real trained models, the real 8,000-applicant dataset, and a live Postgres instance: (1) both models load and produce valid `[0, 1]` probabilities for real applicants (INDIVIDUAL 5,449 / MSME 2,551 — sums to exactly 8,000, confirming full, non-overlapping pipeline coverage); (2) SHAP's per-feature decomposition was checked to **exactly reconstruct** `model.predict_proba()`'s real output for a real applicant in each pipeline (within 1e-4), not just "produced some numbers"; (3) `apply_recalibration()` was shown to flip a probability across a real risk-grade boundary (B→C) via a persisted, versioned, audit-logged DB offset, then cleanly reverted; (4) the admin-weighted composite signal was confirmed to vary genuinely across 200 real applicants (197 distinct values, not a near-constant) and to change for the same applicant purely from an `edit_weighted_field()` weight change — no retraining involved, confirming CLAUDE.md §3.6's core design promise actually holds. Training metrics: INDIVIDUAL AUC 0.930 / F1 0.848, MSME AUC 0.927 / F1 0.836 — both models' single strongest feature is `negative_severity_ratio`, consistent with real credit-risk intuition (hard-negative severity dominating) despite the label being synthetic.

- **Decision hierarchy & exception workflow (Phase 6) — done and verified against real applicant data and a live Postgres instance.** `src/rules/exceptions.py` layers the exception workflow on top of Phase 4's rules engine (kept separate to avoid a circular import — resolving an exception needs to re-fire `evaluate_application()`, and that function has no reason to know about the `exceptions` table).
  - **`route_exception()`** auto-creates one `Exception_` row per `EXCEPTION_REQUIRED` decision, at whatever severity `resolve_decision()` already computed (including any count-based escalation, e.g. `CREDIT_HEAD` from enough distinct fired exception groups) — one review per case, not one per fired rule, since a credit officer reviews the whole flagged picture at once. Routed to a level-scoped placeholder queue (`credit_ops_l1`/`credit_ops_l2`/`credit_head`).
  - **`resolve_application_exception()`** is the resolution endpoint: validates the exception is still `PENDING` (raises otherwise — no double-processing), records the human verdict, and unconditionally re-fires the decision per TODO.md's own wording. Deliberately **honest about what re-firing does and doesn't mean**: a human approving an exception does NOT retroactively relabel the original `Decision.outcome` (still literally `EXCEPTION_REQUIRED` forever — relabeling it `STP_APPROVED` would misrepresent a human-reviewed case as one that was never touched, since STP means "straight-through" by definition). The human verdict lives on `Exception_.status` instead; `effective_outcome()` composes the two into one "is this application cleared to proceed" answer for later phases (7-9) to use, without collapsing them into a single possibly-misleading value.
  - **A real reproducibility gap caught and fixed while designing the re-fire.** Phase 3's `Application` only snapshotted `normalized_profile_snapshot` (master fields) and `feature_vector_snapshot` (engineered vector) — neither includes the raw bureau/bank fields (e.g. `bureau_score`) that Phase 4 already found rules need directly. A re-fire relying only on those two columns would silently drop bureau/bank-based rules from evaluation. Fixed by adding `Application.rule_context_snapshot` (new column, Alembic migration `0cfb3627b26f`) — the exact flat context `build_rule_context()` produces, kept in sync by `evaluate_application()` on every run. `evaluate_application()` itself now supports a snapshot-only re-fire mode (`master_row`/`feature_vector_row` omitted → reads `application.rule_context_snapshot` directly), and now returns `(Decision, ResolvedDecision)` as a pair rather than just the `Decision`, so callers get the resolved severity/escalation directly instead of re-parsing `triggered_rules` JSON to recover something already computed in the same call.
  - **Verified with `test_exception_workflow.py`** against real applicant data and a live Postgres instance: found a real applicant producing a plain L1 exception and a real applicant whose fired-exception-group count triggers escalation to `CREDIT_HEAD` — both routed to the correct level and queue. Approved the L1 exception via `resolve_application_exception()`, confirmed the re-fire ran from the stored `rule_context_snapshot` alone (no fresh profile data passed in at all) and produced a new, properly chained `Decision`; confirmed from a fresh session that the *original* decision's `outcome` was never rewritten. Confirmed `effective_outcome()` composes correctly across all four `Decision.outcome` values plus both exception-resolution states. Confirmed resolving an already-resolved exception raises rather than silently double-processing.
  - Also re-verified `test_rules_engine.py` still passes after `evaluate_application()`'s return-type change (now returns a tuple) — caught and fixed one now-stale assumption in that test itself along the way (`assert len(both_versions) == 2`, which only held on a pristine, never-rerun DB; the DB now legitimately accumulates rule-version history across every phase's re-run of that test, so the assertion was tightened to check the *latest two* versions specifically rather than a total count).

3. **Applicant-type mix drifts from the 50/20/27/3 target after CopulaGAN resampling** (observed ~44/24/28/4 on the latest run). The Faker/prior seed rows are generated at the exact target weights, but CopulaGAN samples from the fitted joint distribution rather than preserving marginal category weights exactly — expected GAN behavior, not a generator bug, but worth knowing if Phase 5 model training wants closer-to-target class balance (could reweight or stratify-resample post-generation if it matters later).
4. **CopulaGAN cross-field decorrelation is a recurring failure mode, not a one-off** — three separate instances found and fixed so far (DPD-label vs. max_dpd, hard-negative flags vs. max_dpd, requested_loan_amount vs. applicant_type). Any other independently-sampled column whose real-world value should be constrained by another column (e.g. GST fields vs. applicant_type, income components vs. applicant_type) is a candidate for the same bug and should be spot-checked, not assumed correct, before being relied on by Phase 4's rules engine.
