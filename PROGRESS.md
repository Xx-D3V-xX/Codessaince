- **Database schema (Phase 3) — done and verified against real Postgres.** `src/db/models.py` defines all 8 tables via SQLAlchemy 2.0 declarative models: `applications`, `rules`, `decisions`, `exceptions`, `audit_log`, `eligibility_multipliers`, `pricing_bands`, `recalibration_offsets`. Alembic (`alembic/`) manages versioned DDL migrations, with `alembic/env.py` wired to `src/db/models.Base.metadata` for autogenerate and to `src/db/session.DATABASE_URL` for connection config (read from `.env`/environment, see `.env.example`). `docker-compose.yml` runs a dedicated `creditgate-postgres` container on port 5434 (deliberately not 5432 — an unrelated pre-existing Docker stack on this machine already occupies 5432/5433, and this schema was kept fully isolated from it). `src/db/audit.py::write_audit_log()` is the one shared audit_log write path TODO.md's checklist calls for.
  - **Schema decisions carrying CLAUDE.md forward into DDL**: `rules`/`eligibility_multipliers`/`pricing_bands`/`recalibration_offsets` all share the same versioning shape — a stable logical `*_code` string plus an incrementing `version` int, unique together, edited by inserting a new row and closing out the old one's `effective_to`/`active`, never by UPDATE — per CLAUDE.md §3.5. `decisions` chains re-runs via `superseded_by_decision_id` rather than overwriting, so a rule-threshold change and re-run leaves both decision versions independently queryable — this is a schema-level guarantee, not something Phase 4's application logic has to get right on its own. `decisions.rule_version_snapshot`/`triggered_rules` are JSONB, not normalized joins to `rules` — a decision has to stay reconstructable exactly as it was even after `rules` moves on to newer versions of the same rule_codes it referenced. `applicant_pipeline` (INDIVIDUAL/MSME, CLAUDE.md §3.1's two-pipeline split) is kept as a separate, coarser enum from `applications.applicant_type` (SALARIED/SELF_EMPLOYED/MSME/CORPORATE) deliberately — which raw type maps to which pipeline is a rules-engine decision (Phase 4), not a schema-level constant.
  - **Added `AssetsRecord`-style rigor here too**: no code change needed, but worth noting the schema was designed to consume Phase 0-2's applicant_id as a plain string FK-less reference (`applications.applicant_id`), not a foreign key into another database — Phases 0-2's parquet-based data and this Postgres schema are deliberately separate concerns until Phase 8's API layer bridges them at ingestion time.
  - **One real bug caught and fixed during downgrade/upgrade round-trip testing** (not assumed correct from `alembic revision --autogenerate` output): the autogenerated `downgrade()` dropped all 8 tables but left every Postgres ENUM type it had created (`applicant_type`, `applicant_pipeline`, `exception_level`, etc.) orphaned, because those types are shared across multiple tables (e.g. `applicant_pipeline` is used by 4 different tables) and Alembic's autogenerate only diffs table-level DDL, not shared type lifecycle. Re-running `upgrade head` after a downgrade then failed with `psycopg2.errors.DuplicateObject: type "applicant_type" already exists`. Fixed by adding explicit `sa.Enum(name=...).drop(bind, checkfirst=True)` calls for all 8 enum names at the end of the migration's `downgrade()`. Verified with a full `downgrade base` → `upgrade head` round-trip: 0 orphaned types after downgrade, all 8 tables recreated cleanly on re-upgrade.
  - **Verified with a real end-to-end smoke test against the live container** (not just "migration ran without error"): created a rule (v1, bureau_score < 650 → HARD_REJECT), an application, and a decision that hard-rejects against it; simulated PS-1 demo scenario 5 exactly (judge lowers the threshold live — inserted rule v2 with threshold 600, closed out v1's `effective_to`/`active` rather than mutating it) and re-ran the same application, producing a second decision (STP_APPROVED) chained to the first via `superseded_by_decision_id`; added a third decision plus a full exception workflow (PENDING → APPROVED with `resolved_by`/`resolved_at`). Every one of those 5 state-changing actions wrote through `write_audit_log()`. Re-queried all of it from a **fresh session** (genuine DB round-trip, not in-memory state) and asserted: both decision versions independently queryable with correct `is_current`/`superseded_by_decision_id` linkage, both rule versions preserved (old row untouched, `active=False`), exactly 5 audit_log rows in the right order, and the exception resolved correctly. All assertions passed. Smoke-test rows were truncated afterward, leaving the schema empty and ready for Phase 4.

## Known issues / mismatches identified (not yet resolved)

1. **`src/scoring/trainer.py` is fully disconnected from `src/features/engine.py`.** It has its own hand-rolled feature engineering and its own hardcoded-threshold proxy-label logic (`risk_score = np.where(bureau_score < 600, ...)`), reproducing the exact anti-pattern this project was designed to avoid. **Confirmed: `trainer.py` is being ignored/rebuilt from scratch, not patched (see Phase 5).**
2. **No rules engine, orchestrator, API, or frontend exist as code yet.** The database schema (Phase 3) is now implemented (see above) — CLAUDE.md §3.4 (conflict resolution precedence) and §3.6/3.7 (weighted-scoring layer, recalibration) remain design-complete but implementation-not-started until Phases 4-5.
3. **Applicant-type mix drifts from the 50/20/27/3 target after CopulaGAN resampling** (observed ~44/24/28/4 on the latest run). The Faker/prior seed rows are generated at the exact target weights, but CopulaGAN samples from the fitted joint distribution rather than preserving marginal category weights exactly — expected GAN behavior, not a generator bug, but worth knowing if Phase 5 model training wants closer-to-target class balance (could reweight or stratify-resample post-generation if it matters later).
4. **CopulaGAN cross-field decorrelation is a recurring failure mode, not a one-off** — three separate instances found and fixed so far (DPD-label vs. max_dpd, hard-negative flags vs. max_dpd, requested_loan_amount vs. applicant_type). Any other independently-sampled column whose real-world value should be constrained by another column (e.g. GST fields vs. applicant_type, income components vs. applicant_type) is a candidate for the same bug and should be spot-checked, not assumed correct, before being relied on by Phase 4's rules engine.

## Decisions made, not yet reflected in any code beyond Phase 0

- DPD history window: **24 months** (not 12) — matches real bureau reporting convention, was 12 in the old generator only because it borrowed `HISTORY_WINDOW_MONTHS` from the AA/bank-statement constant, not a deliberate choice for bureau data specifically. Implemented in Phase 0.
- Two-model split confirmed: individual/salaried pipeline vs. MSME pipeline, **both ML model and rules engine branch by applicant type**. Not yet implemented — applies from Phase 4/5 onward.
- Training feature architecture: ML consumes `EngineeredApplicantFeatureVector` (derived, now including Phase 2's cross-source fields) + a small set of raw passthrough fields (declared income, requested amount, age) — not a fully separate hand-rolled feature set like the old `trainer.py`. Cross-source features now exist (Phase 2, above); trainer.py rebuild itself is still not implemented — applies from Phase 5.
